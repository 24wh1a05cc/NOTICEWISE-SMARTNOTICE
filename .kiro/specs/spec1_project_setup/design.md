## 1. Architecture Overview

NoticeWise follows **feature-first clean architecture**. The application is divided into self-contained feature modules. Each feature owns its data access (repositories), domain logic, and presentation layers. Cross-cutting concerns live in `core/` and `app/`.

### 1.1 Layered Responsibilities

```
Presentation Layer  → Widgets, Screens, Riverpod Providers (AsyncNotifier/StateNotifier)
Application Layer   → Controllers, use-case-level orchestration (inside feature providers)
Domain Layer        → Models (Freezed), repository interfaces, failure types
Data Layer          → Repository implementations, Firebase datasources, DTOs
```

Widgets are always pure: they observe Riverpod state and dispatch events. They never call Firebase, Firestore, Storage, FCM, or any AI endpoint directly.

### 1.2 Dependency Direction

```
Presentation → Domain ← Data
                 ↑
              Application
```

The domain layer has no dependencies on Flutter or Firebase. Repository interfaces live in the domain layer; implementations live in the data layer and are injected via Riverpod.

**Rationale for feature-first over layer-first:**
- Each feature can be reviewed, tested, and developed independently.
- Avoids the common problem where a layer-first structure creates cross-feature coupling in the `repositories/` or `models/` layers.
- Aligns with Riverpod's provider-per-feature model.

| `firebase_auth` | `^5.2.0` | Authentication | Spec 2 |

| `firebase_storage` | `^12.2.0` | File storage | Attachments |
| `firebase_messaging` | `^15.1.0` | Push notifications | Spec 6 |
| `flutter_dotenv` | `^5.1.0` | Environment config | Readable `.env` files; gitignored |

| `json_annotation` | `^4.9.0` | JSON serialization | Pairs with freezed for DTO serialization |
| `gap` | `^3.0.1` | Spacing widget | Cleaner than `SizedBox(height: x)` everywhere |
| `cached_network_image` | `^3.4.0` | Image caching | Smooth image loading for notice thumbnails |
| `logger` | `^2.4.0` | Logging | Colored, leveled console output |

### 3.2 Dev Dependencies

| Package | Purpose |
|---|---|
| `build_runner` `^2.4.12` | Code generation runner |
| `riverpod_generator` `^2.4.3` | Generates Riverpod providers from `@riverpod` annotations |
| `freezed` `^2.5.7` | Generates immutable data classes |
| `json_serializable` `^6.8.0` | Generates `fromJson`/`toJson` |
| `mocktail` `^1.0.4` | Test mocking (no codegen required) |
| `fake_cloud_firestore` `^3.0.2` | In-memory Firestore for repository tests |
| `firebase_auth_mocks` `^0.14.0` | Mock Firebase Auth for tests |
| `flutter_lints` `^4.0.0` | Base linting ruleset |

**Why `mocktail` over `mockito`:** `mocktail` requires no code generation, reducing dev-dependency complexity. Its API is nearly identical to `mockito` so migration is low-cost if needed.

**Why `freezed` over plain classes:** Immutable models with structural equality and `copyWith` are central to the Riverpod state model. The codegen cost is paid once; maintainability benefit is ongoing.

**Why `go_router` over Navigator 2.0 directly:** go_router provides a declarative URL-based routing API compatible with Flutter's Navigator 2.0 without requiring manual `RouterDelegate` and `RouteInformationParser` boilerplate.

## 4. Application Initialization Flow

```
main()
  └─ WidgetsFlutterBinding.ensureInitialized()
  └─ await dotenv.load(fileName: ".env")          ← load env vars
  └─ await Firebase.initializeApp(
         options: DefaultFirebaseOptions.currentPlatform)
  └─ runApp(
       ProviderScope(
         observers: [if (kDebugMode) AppProviderObserver()],
         child: NoticeWiseApp(),
       )
     )

NoticeWiseApp (ConsumerWidget)
  └─ reads: themeNotifierProvider (current ThemeMode)
  └─ reads: routerProvider (GoRouter instance)
  └─ MaterialApp.router(
       theme: AppTheme.light,
       darkTheme: AppTheme.dark,
       themeMode: themeMode,
       routerConfig: router,
     )
```

**Firebase initialization strategy:**
- `firebase_options.dart` is generated by `flutterfire configure` and committed **only after** any embedded API keys are reviewed and accepted as safe.
- For CI/CD or environments without a real Firebase project, a compile-time guard checks for placeholder values and shows an informative error.

## 6. State Management Approach

### 6.1 Riverpod Philosophy

- All providers are created using `@riverpod` code-generation annotation.
- `keepAlive: true` on providers that must survive navigation (e.g., auth state, router).
- `AsyncNotifier` is the default for providers with async initialization.
- `Notifier` for purely synchronous state (e.g., theme mode).

### 6.2 Theme Mode Provider (Spec 1 only provider)

```dart
@Riverpod(keepAlive: true)
class ThemeNotifier extends _$ThemeNotifier {
  @override
  ThemeMode build() => ThemeMode.system;

  void setTheme(ThemeMode mode) => state = mode;
}
```

This allows the placeholder home screen to have a functional theme toggle, demonstrating the Riverpod pattern before real features are introduced.

### 6.3 Provider Observer

In debug builds, a `ProviderObserver` logs provider state changes to the console:

```dart
class AppProviderObserver extends ProviderObserver {
  @override
  void didUpdateProvider(ProviderBase provider, Object? previousValue,
      Object? newValue, ProviderContainer container) {
    logger.d('[Provider] ${provider.name}: $previousValue → $newValue');
  }
}
```

## 7. Material 3 Theme System

### 7.1 Color Strategy

All colors are derived from a single seed color via `ColorScheme.fromSeed`:

```dart
// Light theme
ColorScheme.fromSeed(
  seedColor: AppColors.brandBlue,
  brightness: Brightness.light,
)

// Dark theme
ColorScheme.fromSeed(
  seedColor: AppColors.brandBlue,
  brightness: Brightness.dark,
)
```

`AppColors.brandBlue = const Color(0xFF1565C0)` — institutional blue, suitable for an education/notice context. Adjustable post-approval.

### 7.2 Typography

Material 3 default type scale is used. Custom overrides (if any) defined in `app_text_styles.dart` and applied via `ThemeData.textTheme`.

### 7.3 Component Overrides

Minimal overrides in Spec 1; key overrides will be added progressively as screens are built. Platform for component style decisions:

- `CardTheme`: slight elevation, rounded corners (12dp radius)
- `AppBarTheme`: surface-colored, no drop shadow (MD3 style)
- `InputDecorationTheme`: filled style for form fields

### 7.4 Theme Consumption Rule

No widget may use a hard-coded color. All colors must come from `Theme.of(context).colorScheme.*`. This is enforced by a lint comment in `app_colors.dart` and documented in the steering file.

## 8. Firebase Configuration Boundaries

### 8.1 What is configured in Spec 1

- `firebase_core` added as dependency.
- `Firebase.initializeApp()` called in `main.dart`.
- `firebase_options.dart` placeholder or generated file structure documented.

### 8.2 What is NOT configured in Spec 1

- Firestore collections or Security Rules (Spec 3+)
- Firebase Authentication setup (Spec 2)
- FCM token registration (Spec 6)
- Storage buckets (Spec 4)

### 8.3 FirebaseOptions Strategy

**Preferred:** Run `flutterfire configure` to generate `lib/app/firebase/firebase_options.dart`. This file contains platform-specific Firebase configuration (API keys for the mobile SDKs — note: mobile SDK API keys are not secret in the same way as server keys, but should still be kept out of public repos).

**Alternative (CI/CD):** Pass Firebase config via `--dart-define` at build time and construct `FirebaseOptions` manually. This requires no committed config file.

**Chosen approach:** `flutterfire configure` approach for development; `--dart-define` strategy documented in README for CI/CD pipelines.

## 11. Error Handling Conventions

### 11.1 `AppException` Hierarchy

```dart
// lib/core/errors/app_exception.dart

sealed class AppException implements Exception {
  const AppException({required this.message, this.code, this.cause});
  final String message;
  final String? code;
  final Object? cause;
}

final class NetworkException extends AppException {
  const NetworkException({super.message = 'Network error', super.code, super.cause});
}

final class AuthException extends AppException {
  const AuthException({required super.message, super.code, super.cause});
}

final class DatabaseException extends AppException {
  const DatabaseException({required super.message, super.code, super.cause});
}

final class StorageException extends AppException {
  const StorageException({required super.message, super.code, super.cause});
}

final class UnknownException extends AppException {
  const UnknownException({super.message = 'An unexpected error occurred', super.cause});
}
```

### 11.2 Repository Return Convention

All repository methods that can fail must return `AsyncValue<T>` from Riverpod (preferred) or use a `Result<T>` pattern. Raw exceptions must never propagate from the data layer to the presentation layer uncaught.

Example:
```dart
// Domain interface
abstract class NoticeRepository {
  Future<List<Notice>> fetchNotices({required int limit, DocumentSnapshot? lastDoc});
}

// Riverpod provider wraps repository call
final noticeListProvider = AsyncNotifierProvider<NoticeListNotifier, List<Notice>>(...);
// AsyncValue.loading / AsyncValue.data / AsyncValue.error handled in UI
```

### 11.3 Logging Convention

```dart
// DEBUG:   development-only diagnostic info
// INFO:    significant state transitions
// WARNING: recoverable issues
// ERROR:   caught exceptions that affect user experience
logger.d('message'); // debug
logger.i('message'); // info
logger.w('message'); // warning
logger.e('message', error: e, stackTrace: st); // error
```

## 12. Logging Strategy

`logger` package is used. A singleton `AppLogger` is created in `lib/core/utils/logger.dart`.

```dart
import 'package:logger/logger.dart';
import 'package:flutter/foundation.dart';

final logger = Logger(
  level: kReleaseMode ? Level.warning : Level.debug,
  printer: PrettyPrinter(methodCount: 2, errorMethodCount: 8),
);
```

In release builds, only `warning` and above are printed, reducing log noise and avoiding accidental debug data exposure.

## 13. Localization Strategy

**Decision: String constants class for MVP.** Justification:

- Speeds up initial development; no ARB file management overhead.
- All strings are in one place (`app_strings.dart`), easy to audit.
- Migration to `flutter_localizations` + ARB is straightforward: replace constant references with `AppLocalizations.of(context).key`.

```dart
// lib/core/constants/app_strings.dart
abstract class AppStrings {
  static const appName = 'NoticeWise';
  static const tagline = 'Smart Notice Management';
  // ... per-screen strings added as screens are built
}
```

If multi-language support is required before Spec 10, the strategy can be upgraded. A `// TODO(i18n): replace with ARB` comment will be placed in `app_strings.dart`.

## 15. Key Technical Decisions Summary

| Decision | Choice | Rationale |
|---|---|---|
| State management | Riverpod (codegen) | Best-in-class Flutter DI + async state |
| Navigation | go_router | Declarative, URL-based, official support |
| Immutable models | freezed | Code-gen, null-safe, `copyWith`, equality |
| JSON serialization | json_serializable | Pairs with freezed; standard approach |
| Testing mocks | mocktail | No codegen required; clean API |
| Env config | flutter_dotenv | Readable; familiar `.env` convention |
| Logging | logger package | Leveled, colored, release-safe |
| Linting | flutter_lints + extras | Balance of strictness and productivity |
| Localization | AppStrings constants | Pragmatic for MVP; extensible |
| Architecture | Feature-first clean | Independent features; scalable team |
| Firebase options | flutterfire configure | Standard toolchain; well-documented |
